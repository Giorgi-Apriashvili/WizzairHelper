# WizzairHelper — decisions and deliberate deviations

Authority (00-README): 07 applies across the package; each numbered chapter is authoritative for its
subsystem; 05 holds the acceptance inputs/outputs. Where the documents disagree, the resolutions
below are binding for this code base. Each entry names both sides.

## Toolchain and structure

| # | Decision | Reason |
|---|---|---|
| D-01 | **C++23**, not the C++20 named in 06 §1. | User decision (2026-11-15). |
| D-02 | All third-party dependencies via the pinned vcpkg submodule, **including Qt** (qtbase 6.11.2); libcurl with Schannel + brotli; GoogleTest. ICU is the Windows system `icu.dll` (02 §4.3), not a vcpkg port. | User decision; ICU is an OS component and matches .NET-on-ICU behaviour. |
| D-03 | `wizzairhelper_core` is pure (no I/O, no threads). The place resolver's geocoding and the flight search service live in `wizzairhelper_services` because they perform I/O / own worker threads. The offline place matching (catalog) stays in core. | 06 §1 lists place resolution and the engine under core, but also requires core to have only abstract I/O interfaces; this split keeps core pure and both libraries are test-drivable. |
| D-04 | Qt 6 has no `QWinTaskbarProgress`; taskbar progress uses `ITaskbarList3` COM directly (01 §10.9). Qt's progress bar does not lag like the native control, so the "jump past, then back" trick (01 §10.6) is kept only where harmless. Win32 calls in 01 describe required *behaviour*. | 06 mandates Qt Widgets; 01 describes the predecessor's Win32 mechanics. |

## Naming and emulation notes

| # | Topic | Decision |
|---|---|---|
| D-25 | `AirportCatalog.Near` | Exposed as `airports_near(point, radius_km)`: `<windows.h>` defines `near` as an empty macro, which breaks any member named `near`. |
| D-26 | Hand-written replacements for the .NET regexes (`CityNameOfFake`, `TrailingCodeRegex`, `ExtractApiUrl`) | Mirror .NET semantics exactly (verified against .NET 10): `\s` = `char.IsWhiteSpace`, `\d` = any BMP decimal digit, `\b` word characters = L*, Mn, Nd, Pc, U+200C/U+200D per UTF-16 unit, IgnoreCase = en-US case equivalences. No `std::regex`. |
| D-27 | Amount that does not fit a decimal in a timetable | `json::FormatError` with the .NET text "One of the identified items was in an invalid format."; the client wraps any `json::Error` as `Wizz Air sent a timetable that could not be read: …` (04 §9.2). |
| D-28 | Unpaired surrogate escapes in JSON strings (`"\ud800"`, `"\udc00"`) | As on .NET 10 (verified): `JsonDocument.Parse` accepts them (the RFC 8259 grammar does), only reading that text throws `InvalidOperationException`. `json::parse` keeps such a string as an unreadable value of kind String: `as_string`, `get_string` and `Member::name` throw `json::TypeError` with the .NET text — `Cannot read incomplete UTF-16 JSON text as string with missing low surrogate.` for a high surrogate not followed by another `\u` escape; `Cannot read invalid UTF-16 JSON text as string. Invalid surrogate value: '0x…'.` (format `X2`) naming a leading low surrogate, or the escape after a high surrogate when that is not a low one. The first problem in a string wins; everything else in the document stays readable, so junk in a field nobody reads no longer rejects the route map (02 §5.1) or a Photon answer (02 §6.4, §6.6). `find` / `get_string` scan the members from the last to the first (last duplicate wins) and throw when they reach a name holding an unpaired surrogate before a match; .NET's `TryGetProperty` throws there only when the escaped name is longer than the requested one and agrees with it up to its first backslash. Consumers keep their .NET catch clauses (e.g. `ParseValidationCodes` catches only `JsonException`, so the TypeError propagates); where .NET reads through `JsonSerializer` (settings.json, geocode.json), which wraps it in a `JsonException`, it is handled as one — unknown properties are skipped unread there. Malformed or truncated escapes and raw UTF-8 surrogates stay `ParseError`s; the writer is unchanged. |
| D-29 | Unreadable text inside a 400 `validationCodes` body (D-28) | `parse_validation_codes` treats any JSON read error as "no codes", so the response classifies as an ordinary 400 `WizzApiError` (04 §11.3 row 4b). .NET would let the InvalidOperationException escape and end the search with an unexpected error; CT-SRCH-04's intent (malformed responses are API errors, never crashes) wins. |

## Command line, version, packaging and releases

| # | Topic | Decision | Reason |

| D-35 | `--version` (a small extension of the 01 §17.1 command line) | An argument equal to `--version` anywhere on the command line (exact and case-sensitive, like the 01 §17.1 flags) prints exactly `WizzairHelper X.Y.Z` and a line feed (X.Y.Z = project(VERSION), D-37) to standard output and exits with 0 before anything else: no window, settings, network, crash reporter or AppMutex. ## Self-updater

The core lives in `wizzairhelper_services` (`wizz/services/updater.hpp`, namespace `wizz::update`,
Qt-free). It follows the owner's "Self-updating apps" rules and the installer / updater contract
shared with the packaging work: stable asset names `WizzairHelper-X.Y.Z-win64-setup.exe`,

has no updater; nothing here changes a specified behaviour, apart from the three update options
added to settings.json (D-60). The user's options are plain values in `wizz/services/update_options.hpp`.

The **same** address means Wizz Air really is busy: it is written again (its 24 hours start over), the usual retries follow (5, 15 and 30 s, with the gate cooled down), and later 503s of that call are not checked again. If discovery fails, the address in use is kept (checked now, so no new check for 10 minutes, and expiring in 1 hour) and retried as usual. A call cancelled meanwhile stops at the lock and looks nothing up. JSON 503s, 408, 429, 500, 502 and 504 are unchanged, and so is the 404 path (§11.3 row 3, §7.5). **Age:** an address is remembered as `ApiAddress{url, checked_at, expires}` and expires `WizzClientOptions::api_url_max_age` (24 h) after it was found or checked, in memory and on disk. The age of `api-url.txt` is its last write time (`FileCache::written_at`; a time in the future counts as now). Only discovery writes the file; reading never re-writes it (CT-API-14). A check time in memory that lies in the future (the clock was set back) counts as old, both for the expiry and for the 10-minute guard. An expired address is looked up again. If that look-up fails, the older address is used and kept for 1 hour (`kLookUpRetryAfter`) before the next try. With no known address the `WizzApiError` propagates as before. **Accepted:** (a) a look-up holds the discovery lock, so while wizzair.com hangs, the other calls that need it wait: up to the three discovery pages' timeouts (about 90 s) once, then again an hour later while it still hangs. (b) `invalidate_api_url` stays lock-free (§7.5): if one call meets a 404 on the address while another call's look-up after a 503 fails, the failed look-up can keep that address for an hour. Both calls fail in that moment anyway, because wizzair.com cannot be read. The next call's own 404 discards the address again, and once wizzair.com answers, its look-up finds the new one. | CloudFront answers a retired version with 503, so the 404 rule never fired. The 10-minute guard keeps a 503 that comes right after discovery a plain "busy" (CT-API-05, the `cancel_retrying` replay). It also limits a Wizz Air that really is busy to one extra look-up per 10 minutes: one homepage request while wizzair.com answers, and all three pages while it does not. The 24-hour age limits how long a retirement the client cannot recognise (any other answer) can last, and costs one homepage request a day. | D-58 | Text rendering (2.1.0) | **Natural, slightly heavier**, the owner's choice (2026-11-17) after comparing the candidates in the real app at 1:1. Every font is drawn with `QFont::PreferNoHinting`, which Qt 6.11's DirectWrite engine draws as ClearType natural symmetric with grid fitting off (`DWRITE_GRID_FIT_MODE_DISABLED`): curves and diagonals are smoothed vertically too and glyphs sit at fractional positions. Every face with a weight axis ("wght": Segoe UI Variable 300–700, Cascadia Mono 200–700) is drawn 50 units heavier than the face Qt picks for the font's families and weight (`style::weight_axis_for`: QFontInfo's weight of the font without the axis, + 50, within the axis' range): regular 450, semibold 650 (the semibold families have one face, so a bold copy of one stays 650), Bold 700, the axis' maximum. Faces without a weight axis (Windows 10's Segoe UI and Consolas, `WIZZ_FONTS=windows10`) are plain natural, as the comparison page the owner chose from said ("Windows 10 gets plain natural with Segoe UI"): there natural loses ink with nothing to win it back (`--fonts windows10` captures, the same 13 round-trip rows: 88 % of 2.0.0's total ink, mean coverage 0.63 → 0.55, vertical smoothing 54 % → 68 %), and `WIZZ_TEXT_RENDERING=hinted` gives 2.0.0's text back. **How it reaches every text**: ui_style's fonts name their face (their families, and the regular ones their weight, `QFont::Normal`) and have the hinting and the axis as their own, so `resolve()` keeps them: resolved against a bolder font (a model's Qt::FontRole, `QPainter::setFont`, a widget's own font under its parent's) they draw as built. `fit_text_rendering` makes the axis a font's own only where the font names its families; a font that takes its families from the font it is resolved against takes that font's axis along. The application font is one of them (D-53: it replaces Qt's per-class fonts). A copy of a font keeps its axis, so a bolder or lighter copy would draw at the wrong weight (a setBold() copy of the UI font at 450, i.e. regular; the semibold family on a default-constructed QFont, which copies the application font, at 450 instead of 650): an application event filter (`style::keep_text_rendering`) fits every widget's font on Polish and FontChange, in every look, Qt's own setBold() copies (the calendar's month and year buttons) included; a child that inherits an unfitted font is left to its parent, whose FontChange follows, so no child keeps an inherited weight as its own. ModernStyle measures and draws menu items in a fitted font and draws a menu's default action bold, as Windows and Fusion do. QHeaderView sizes a section with a setBold() copy of the semibold header font, which picks the same face: it measures what it draws. Apart from menu items, painting does no font work of its own. Rich text would be one more copy that nothing fits (a `<b>` or font-weight makes a text format of its own, drawn at the regular axis): every label, message box and tooltip of the app is plain text, and `TextRendering.*` fails on a visible rich-text label. **High Contrast** keeps the rendering: D-55 changes the colours and the style, not the app font, the heavier strokes help contrast too, and a live switch keeps one set of metrics; the plain style's own bold copy for a menu's default action is not fitted, and no menu of the app has one (`TextRendering.*` checks). **Measured** in the real app (`check_autotest.py` captures, the same 13 rows of the round-trip grid in each; vertical smoothing = the share of the ink pixels at the top or bottom edge of a stroke that are only partly covered): at 100 % `hinted` (2.0.0) 49 %, `natural` 68 %, natural-heavier 67 % (dark the same); the mean coverage of an ink pixel 0.63 / 0.54 / 0.57 and the total ink 100 % / 97 % / 105 %: natural loses ink, 50 units of weight win it back.
