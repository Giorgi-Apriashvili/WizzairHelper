# WizzairHelper — decisions and deliberate deviations

Authority (00-README): 07 applies across the package; each numbered chapter is authoritative for its
subsystem; 05 holds the acceptance inputs/outputs. Where the documents disagree, the resolutions
below are binding for this code base. Each entry names both sides.

## Toolchain and structure

| # | Decision | Reason |
|---|---|---|
| D-01 | **C++23**, not the C++20 named in 06 §1. | User decision (2026-11-15). |
| D-02 | All third-party dependencies via the pinned vcpkg submodule, **including Qt** (qtbase 6.11.2); libcurl with Schannel + brotli; GoogleTest. ICU is the Windows system `icu.dll` (02 §4.3), not a vcpkg port. | User decision; ICU is an OS component and matches .NET-on-ICU behaviour. |
| D-03 | `wizzairhelper_core` is pure (no I/O, no threads). The place resolver's geocoding and the flight search service live in `wizzairhelper_services` because they perform I/O / own worker threads. The offline place matching (catalog) stays in core. | 06 §1 lists place resolution and the engine under core, but also requires core to have only abstract I/O interfaces; this split keeps core pure and both libraries are test-drivable. |
| D-04 | Qt 6 has no `QWinTaskbarProgress`; taskbar progress uses `ITaskbarList3` COM directly (01 §10.9). Qt's progress bar does not lag like the native control, so the "jump past, then back" trick (01 §10.6) is kept only where harmless. Win32 calls in 01 describe required *behaviour*. | 06 mandates Qt Widgets; 01 describes the predecessor's Win32 mechanics. |

## Naming and emulation notes

| # | Topic | Decision |
|---|---|---|
| D-25 | `AirportCatalog.Near` | Exposed as `airports_near(point, radius_km)`: `<windows.h>` defines `near` as an empty macro, which breaks any member named `near`. |
| D-26 | Hand-written replacements for the .NET regexes (`CityNameOfFake`, `TrailingCodeRegex`, `ExtractApiUrl`) | Mirror .NET semantics exactly (verified against .NET 10): `\s` = `char.IsWhiteSpace`, `\d` = any BMP decimal digit, `\b` word characters = L*, Mn, Nd, Pc, U+200C/U+200D per UTF-16 unit, IgnoreCase = en-US case equivalences. No `std::regex`. |
| D-27 | Amount that does not fit a decimal in a timetable | `json::FormatError` with the .NET text "One of the identified items was in an invalid format."; the client wraps any `json::Error` as `Wizz Air sent a timetable that could not be read: …` (04 §9.2). |
| D-28 | Unpaired surrogate escapes in JSON strings (`"\ud800"`, `"\udc00"`) | As on .NET 10 (verified): `JsonDocument.Parse` accepts them (the RFC 8259 grammar does), only reading that text throws `InvalidOperationException`. `json::parse` keeps such a string as an unreadable value of kind String: `as_string`, `get_string` and `Member::name` throw `json::TypeError` with the .NET text — `Cannot read incomplete UTF-16 JSON text as string with missing low surrogate.` for a high surrogate not followed by another `\u` escape; `Cannot read invalid UTF-16 JSON text as string. Invalid surrogate value: '0x…'.` (format `X2`) naming a leading low surrogate, or the escape after a high surrogate when that is not a low one. The first problem in a string wins; everything else in the document stays readable, so junk in a field nobody reads no longer rejects the route map (02 §5.1) or a Photon answer (02 §6.4, §6.6). `find` / `get_string` scan the members from the last to the first (last duplicate wins) and throw when they reach a name holding an unpaired surrogate before a match; .NET's `TryGetProperty` throws there only when the escaped name is longer than the requested one and agrees with it up to its first backslash. Consumers keep their .NET catch clauses (e.g. `ParseValidationCodes` catches only `JsonException`, so the TypeError propagates); where .NET reads through `JsonSerializer` (settings.json, geocode.json), which wraps it in a `JsonException`, it is handled as one — unknown properties are skipped unread there. Malformed or truncated escapes and raw UTF-8 surrogates stay `ParseError`s; the writer is unchanged. |
| D-29 | Unreadable text inside a 400 `validationCodes` body (D-28) | `parse_validation_codes` treats any JSON read error as "no codes", so the response classifies as an ordinary 400 `WizzApiError` (04 §11.3 row 4b). .NET would let the InvalidOperationException escape and end the search with an unexpected error; CT-SRCH-04's intent (malformed responses are API errors, never crashes) wins. |

## Planned test-only extensions

| # | Extension | Reason |
|---|---|---|
| D-30 | Hidden `--autotest` companions, approved by the user (2026-11-15), parsed by `wizz::ui::AutoTestOptions` (`src/ui_logic`) and honoured only together with `--autotest`, with the 01 §17.1 matching rules (exact, case-sensitive, first occurrence wins, value = next argument): **`--data-root <dir>`** replaces `%LOCALAPPDATA%\WizzairHelper` as the root of `settings.json`, `errors.log` and `cache\` (isolated profile; `app_paths` takes it as the root override). **`--replay <dir>`** serves every Wizz, FX and geocoder request through `wizz::ui::ReplayTransport` from `<dir>/replay.json` plus the body files it names: ordered rules that match on `method`, `url` (exact), `urlPrefix`, `urlContains`, `bodyContains` and answer with `status` (200), `file` or `body`, `contentType` (by extension; `null` = none), `headers`, `delayMs` (cancellable), `error` (`transport` / `timeout`, with `message`) and `times` (use count); the first matching rule wins; an unmatched request gets 404 `{"message":"No HTTP resource was found"}`; unknown fields are rejected at start-up (full format in `replay_transport.hpp`). **`--fixed-now <yyyy-MM-ddTHH:mm:ss[.fffffff][Z]>`** runs on a `FixedClock` at that UTC instant with the local zone UTC. Relative directories are made absolute against the current directory; a bad `--fixed-now` throws a `FormatError` before the window opens, like a bad `--out` date. Added for the 05 §5 acceptance checks: **`--no-pacing`** drops the 1 s request spacing and its jitter in front of Wizz requests (a replay talks to no server; retry back-offs stay). **`--warm-cache`** runs the outbound search once before the script, so the script's outbound search replays every timetable from the client's memory cache ("cached replay"); summary.json then describes the cached search, and `requestsToWizz` includes the warm-up. **`--cancel-after-ms <n>`** (ASCII digits, at most 9; anything else is a `FormatError` before the window) arms a timer when the script's outbound leg begins fetching (`Controller::leg_started`); when it fires, the runner sends Esc to the focused control, clicks Cancel, sends Esc again and calls the Cancel handler — one cancellation transition must result (D-11). The timer stops with the outbound search, so it never reaches a later search. **`--diagnostics`** writes `diagnostics.json` next to summary.json (format in `autotest_diagnostics.hpp`): the 40 ms timer's gaps (`TimerGapProbe`; the runner's own screenshots are excluded and reported apart), a UI-loop watchdog (`EventWatchdog` through `Application::notify`, R-03), the cancel record, each search's Wizz requests and duration, the final Outbound / Return tables against the stored results, display and DPI data, and a layout check (clipping, overlap, cut text, Cancel visible) at every screenshot. | 05 §5 requires unattended GUI checks on an isolated profile and CI "uses fixtures only", which the documented flags alone cannot provide; it also asks for cancellation at three points, one transition for Esc + Cancel, a measured timer gap under a heavy cached replay and the final tables checked for late rows. Documented flags and `summary.json` stay unchanged. |

## Release and responsiveness

| # | Topic | Decision | Reason |
|---|---|---|---|
| D-31 | Release package (06 §4) | The install rules of `cmake/WizzPackaging.cmake`, packed by the `dist` target (D-38; before that a CPack ZIP). Qt files come from vcpkg's `windeployqt` (`--release --no-translations --no-system-d3d-compiler --no-system-dxc-compiler --no-opengl-sw --no-compiler-runtime --skip-plugin-types generic,networkinformation,tls`): Qt Core/Gui/Widgets, `platforms/qwindows.dll`, `styles/qmodernwindowsstyle.dll` (windowsvista), `imageformats/`. Every other non-system DLL (libcurl, zlib `z.dll`, brotli, pcre2-16, double-conversion, libpng, md4c) is found by `file(GET_RUNTIME_DEPENDENCIES)` over the exe and the deployed plugins. The **MSVC runtime is app-local** (`InstallRequiredSystemLibraries`: msvcp140*, vcruntime140*, concrt140); the UCRT is part of Windows 10/11 and not copied. `THIRD-PARTY-NOTICES.txt`, `README.txt` and `licenses/<port>.txt` (vcpkg's copyright files) are included; ICU is Windows' `icu.dll`. | 06 §4 "verify launch on a clean Windows profile without build tools installed": an app-local runtime needs no administrator install of vc_redist. Qt Network, the TUIO touch plugin, TLS / network-information plugins and the D3D/DXC shader compilers are never used by a Widgets app that does HTTP through libcurl; without `--no-system-dxc-compiler` windeployqt copies 15.7 MB of `dxcompiler.dll` / `dxil.dll` from the Windows SDK on MSBuild's PATH (the ZIP is 11.5 MB without them). |
| D-32 | Worker events of a leg run | Progress reports and row batches of RunLegAsync travel through a `JobMailbox` (`job_runner.hpp`): a worker push posts a delivery only when none is pending, and the delivery takes everything pushed so far, in order, still in the job's FIFO queue before its completion. `BusyPanel::report(span)` runs Report(p) for each report (UpdatesReceived, ETA and notices unchanged) and refreshes once. | 01 §10.3 refreshes on every Report. A fully cached replay posts two events per request within milliseconds (372 for 186 requests); on Windows the 40 ms `WM_TIMER` is only generated when the queue is empty, so the timer starved for 75–150 ms at 200 % (05 §5 limit 100 ms) although no single event took 3 ms. One delivery per burst keeps the queue short; only reports the user could never see (superseded within the same burst) are not drawn. |
| D-33 | First retry notice froze the UI | `FontWarmup` (`font_warmup.hpp`) resolves the busy panel's texts, including the "⏳" of the retry countdown (01 §10.5), on a worker thread at start-up; `main` waits for it before the window is shown. | Segoe UI lacks U+23F3. Qt's first layout of it asks Windows for a fallback font: 0.2–0.4 s on the UI thread (measured, Release), so the spinner froze exactly when the first 503 back-off began (05 §5 cancel_retrying: 400 ms timer gap). Fonts and the fallback cache are process-wide, so the worker pays it while the services and the window are built. |
| D-34 | Idle progress bar | User decision (2026-11-16): when nothing is being processed the bar must be completely still. The "windowsvista" style animates a moving glow over any bar with 0 < value < maximum, and after End the bar rests at 1000 of 1001 (01 §10.3) or part-filled after a failure. `PanelProgressBar` paints normally while the panel is busy (the glow is one more sign of life) and, while idle, draws a full bar clipped to the real fill width, for which the style stops its animation. Values, colours and the fill width are unchanged. |

## Command line, version, packaging and releases

| # | Topic | Decision | Reason |
|---|---|---|---|
| D-35 | `--version` (a small extension of the 01 §17.1 command line) | An argument equal to `--version` anywhere on the command line (exact and case-sensitive, like the 01 §17.1 flags) prints exactly `WizzairHelper X.Y.Z` and a line feed (X.Y.Z = project(VERSION), D-37) to standard output and exits with 0 before anything else: no window, settings, network, crash reporter or AppMutex. It wins over `--autotest` and every other flag (`version_option.hpp`). The exe is a GUI-subsystem program, so the text goes to the standard output handle it inherited (the pipe or file of a caller that captures or redirects it: CreateProcess with `STARTF_USESTDHANDLES`, Python, CMake, cmd redirection, PowerShell **inside a pipeline**) and, when there is none or writing fails, to the console of the parent process (`AttachConsole(ATTACH_PARENT_PROCESS)`), where it appears after the prompt. PowerShell starts a GUI-subsystem program detached, without redirection and without waiting, when it is the last command of a pipeline: `$(& .\WizzairHelper.exe --version 2>&1)` shows the line on the console but captures nothing, `$(& .\WizzairHelper.exe --version 2>&1 \| ForEach-Object { "$_" })` captures it (`tools/release_check.ps1` pipes it so). | `release_check.ps1 -Exe WizzairHelper.exe` and the self-updater read the version of a downloaded or installed copy without starting the app. A console-subsystem exe would be captured in every PowerShell form but opens a console window whenever the app is started from Explorer or the Start menu. |
| D-36 | AppMutex | WizzairHelper.exe creates the named mutex `WizzairHelper.AppMutex` (session namespace, not owned) right after the `--version` check and holds it until the process ends (`app_mutex.hpp`). It is not a single-instance lock: further copies open the same mutex and run (06 §3). A name Windows refuses is ignored. | The installer and its uninstaller (`AppMutex=WizzairHelper.AppMutex`, D-38) can tell that the app is running before files are replaced or removed. |
| D-37 | Single source of the version | `project(WizzairHelper VERSION X.Y.Z)` in `CMakeLists.txt` (configure fails unless it is X.Y.Z). The C++ code gets `WIZZ_VERSION_STRING`; the version resource (`FILEVERSION`/`PRODUCTVERSION` X,Y,Z,0, FileVersion `X.Y.Z.0`, ProductVersion `X.Y.Z`) includes `wizz_version.h`, generated by `src/app/CMakeLists.txt`; the release file names and the installer's AppVersion come from the same variable; CI's tag guard compares `vX.Y.Z` with it. `vcpkg.json` has no `version` (optional in a top-level manifest). | One number to bump per release (`docs/RELEASING.md`). | D-39 | CI and releases | `.github/workflows/build.yml` on `windows-2025-vs2026` for pushes to `main`, `v*` tags and pull requests.
